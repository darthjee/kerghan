# Rewrite projects.md

Rewrite `docs/agents/specs/issues/projects.md` with the decisions of #485, keeping the file's existing header (title, one-line purpose, "Part of the [Issues and Projects specs](../issues.md).") and the rule that "Required tests" is the last section. Suggested sections, in order:

1. **Naming**: one paragraph. "Project" is Kerghan's concept: an application (backed by a repository) or a life/other project (no repository). It is not a GitHub Project; the GitHub feature is always written in full as "GitHub Project". No Kerghan-side term is coined for GitHub Projects (out of scope).
2. **Repository and ownership**: 0 or 1 linked repository (one of the user's repository rows); no repository means a non-code project. One repository backs at most one project per user (unique among non-deleted projects); several projects with no repository are allowed. One owner, set from the session, never from the request; private, so another user's project answers `404`.
3. **Fields**: a table with `name` (required, trimmed, 1 to 100 characters counted in characters, unique per user case-insensitively among non-deleted projects, `409` on a duplicate, blank is a validation error), `description` (optional, trimmed plain text, at most 2000 characters, never rendered as markup, blank stored as none), repository (optional), owner, timestamps, deletion marker. State "no status or archive state in v1". Read model: a repository summary (owner, name, private, row status Added/Unavailable/Unknown) derived on read and never stored on the project; no issue counts or sync info in v1. Column types stay with #486.
4. **Creation paths**: the explicit path and the shortcut exactly as in the issue's Solution (eligible repositories in any derived status; rejection without revealing existence; `409` for a repository that already has a project, pointing at the existing one; the shortcut returns the existing project with `200`, creates with `201`, rejects a not-added repository with `409`, default name `owner/name`, `409` on a name collision, no suffix; creation never enqueues a job or calls GitHub; one shared service method). Routes, payloads and error codes stay with #489.
5. **Linked repository unavailable or removed**: the project never loses its repository automatically; local work continues; sync refused while Unavailable and allowed while Unknown; pending writes stay in their markers under #488's rules; a dangling reference reads like Unavailable with no summary fields; the future "remove an added repository" feature must refuse with `409` while a non-deleted project of the user uses it (note that #492 copies this into `modules/repositories.md`); integration deleted leaves the project untouched; user deleted removes everything including soft-deleted rows (mechanism: #486, #493).
6. **Deletion**: soft delete, `404` and exclusion from listings afterwards, issues kept but unreachable, uniqueness only among non-deleted rows (enforcement for #486), links deleted and their GitHub issues freed, markers discarded, jobs for a deleted project or user are a no-op, confirmation warns and reports the count of issues with unsent changes, no GitHub call, no restore and no purge in v1.
7. **Changing a project later**: edit name and description under the creation rules; attach a repository to a project with none (same checks, never syncs); change or detach refused with `409`; issues cannot move between projects in v1.
8. **Room for sharing, members and roles**: no schema, endpoint or concept in v1; the four guardrails (single access check, issues derive access from their project, owner credentials do the GitHub work, actor not assumed to equal owner).
9. **Edge cases**: the table from the issue (simultaneous creations on one repository or one name, repository with only a deleted project, rename or transfer on GitHub, Unavailable and return, Unavailable at creation, job or request for a deleted project or user), each row with expected behavior and the check that verifies it.
10. **Not decided**: members and roles, invitations, ownership transfer, shared visibility, a member's view when the owner's integration is revoked, archive status, restore and purge of deleted projects, issue moves, change or detach of a repository while no links exist (depends on an unlink action from #487). One line each with the reason (out of scope for the epic, or depends on another issue). No owner issue is invented.
11. **Open questions**: the five items owned by #485 are resolved and removed. Keep the heading with "None." only if the other files do; otherwise drop the heading.
12. **Required tests** (last): one test per rule above: another user's project and a deleted project answer `404`; a project without a repository can be created; a project can link one added repository in any derived status; a not-added or foreign repository is rejected; a repository with a project is rejected (`409`) on the explicit path; the shortcut returns `200` for an existing project and `201` otherwise, rejects a not-added repository, defaults the name to `owner/name` and answers `409` on a collision; creation makes no GitHub call and enqueues no job; name and description rules (trim, length, blank, case-insensitive uniqueness); uniqueness among non-deleted projects and reuse after deletion; soft-deletion effects (links released, markers discarded, jobs a no-op, no GitHub call, removal on user deletion); attach works and rejects a used repository; change or detach is refused; the single access check covers project and issues; owner credentials do the GitHub work; the concurrency cases.

Write plain statements, not code. Do not use real repository names beyond neutral examples such as `owner/name`.
