# Plan: Refactor: Exclude lockfiles from Codacy's Lizard file-size check

Issue: [226-refactor-exclude-lockfiles-from-codacy-s-lizard-file-size-check.md](../../issues/226-refactor-exclude-lockfiles-from-codacy-s-lizard-file-size-check.md)

## Overview
Add a Lizard-scoped exclusion for `yarn.lock` files to `.codacy.yml`, so Codacy stops reporting the generated lockfiles as oversized source files while Trivy keeps scanning them for vulnerable dependencies.

## Context
Codacy's Lizard engine reports `Lizard_file-nloc-medium` (Warning) for `backend/yarn.lock` and `frontend/yarn.lock`. They are generated by Yarn, not hand-maintained. The repo's `.codacy.yml` already holds engine-scoped, commented exclusions for `pmd`, `eslint`, `eslint-8` and `eslint-9`, but no `lizard` block. Codacy's public tools API confirms the engine key is `lizard` (pattern prefix `Lizard_`) and Trivy's is `trivy`, so an `engines.lizard` exclusion leaves Trivy untouched. `.codacy.yml` is a root-level file owned by the architect (issue #225 was implemented the same way).

## Implementation Steps

### Step 1 — Add the `lizard` engine exclusion
Append a new `lizard:` entry under `engines:` in `.codacy.yml`:

```yaml
  lizard:
    exclude_paths:
      # Yarn lockfiles are generated, not hand-maintained, so Lizard's file-size check
      # (`Lizard_file-nloc-medium`) on them is noise. Excluded for Lizard only — never via the
      # top-level `exclude_paths` — so Trivy keeps scanning them for vulnerable dependencies.
      # A glob is safe here (unlike the file-by-file ESLint exclusions) because every
      # `yarn.lock` is generated. See issue #226.
      - '**/yarn.lock'
```

Do not touch the top-level `exclude_paths` (none exists today; do not add one) and do not change the existing `pmd`/`eslint*` blocks.

## Files to Change
- `.codacy.yml` — add the `engines.lizard.exclude_paths` block with `'**/yarn.lock'` and its explanatory comment.
