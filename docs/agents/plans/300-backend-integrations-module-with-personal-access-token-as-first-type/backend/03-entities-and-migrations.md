# Entities and migrations

Implement `model.md` "`integrations` columns" and "Lockout table".

- **`Integration` entity**, table `integrations`:
  - Every column in `model.md`, with the exact names, types, nullability and lengths.
  - `metadata` is a `json` column. The `secret_iv` and `secret_auth_tag` columns are
    `varbinary`, and `secret_ciphertext` is a `blob`, all mapped to `Buffer`.
  - `uuid` is set by the application (`crypto.randomUUID()`), never generated by the DB.
  - `userId` is a plain column, with no relation.
  - Indexes: unique `uuid`, unique `(user_id, label_normalized)`, non-unique `user_id` and
    `secret_key_id`.
- **`IntegrationCredentialLockout` entity**, table `integrations_credential_lockouts`, mirroring
  `AccountEditLockout` (unique `user_id`, `failed_attempts` default 0, nullable `locked_until`).
- **Constants** for the string enumerations (`provider`, `type`, `status`,
  `last_test_result`), validated in code.
- **Migrations**, one per table, named `<timestamp>-integrations-create-integrations.ts` and
  `<timestamp>-integrations-create-credential-lockouts.ts`:
  - Timestamps go after `20260914120010`. Reuse `helpers.ts` (`idColumn`, `createdAtColumn`,
    `updatedAtColumn`).
  - The `integrations` migration also creates the FK `user_id → auth_users(id) ON DELETE
    CASCADE`, with a JSDoc that records it as the deliberate, documented exception to the
    logical-FK strategy (`model.md#owner-foreign-key`).
  - Each `down` drops its table, which drops the FK with it.
  - Don't use `skipInProduction`: these are schema migrations, not seeds.

Specs: migration specs (follow any existing migration spec pattern; if there is none, unit-test
`up` and `down` against a mocked `QueryRunner`). Assert the table, columns, indexes and FK
definitions, and that `down` drops the table.
