# Issue: Refactor: Exclude lockfiles from Codacy's Lizard file-size check

## Description
Codacy's Lizard engine treats generated `yarn.lock` files as source code and reports them as oversized files.

## Problem
`Lizard_file-nloc-medium` (Warning) is reported for `backend/yarn.lock` (5633 non-comment lines at filing time) and `frontend/yarn.lock` (3311). Lockfiles are generated by Yarn, not maintained by hand, so these findings are noise.

## Expected Behavior
- Lizard no longer analyses the repo's `yarn.lock` files.
- Trivy (and any other engine) still scans them — Trivy is the only tool checking them for vulnerable dependencies (see the multer CVE issue).

## Solution
- Add a new `engines.lizard.exclude_paths` block to `.codacy.yml`, with the glob `'**/yarn.lock'` (covers `backend/yarn.lock`, `frontend/yarn.lock`, and any future lockfile; a glob is safe here because lockfiles are always generated, unlike the file-by-file ESLint exclusions), preceded by a comment explaining why (generated files, Lizard-only exclusion so Trivy keeps scanning them, reference to this issue #226) — matching the documented-exclusion style of the existing `pmd`/`eslint*` entries.
- The Codacy engine key is `lizard` (confirmed via Codacy's public tools API; findings prefixed `Lizard_`).
- Do **not** use the top-level `exclude_paths`: that would hide the lockfiles from Trivy as well.
- No other files change. Other Codacy-config issues also edit `.codacy.yml`; rebase on whichever merges first.

## Benefits
Removes 2 Warning findings while keeping dependency vulnerability scanning intact.

## Verification
- After merge, Codacy's re-analysis of `main` no longer reports `Lizard_file-nloc-medium` for either `yarn.lock`.
- Trivy findings for the lockfiles (if any) are still reported.
