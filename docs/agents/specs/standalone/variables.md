# Environment-variable contract

Read by #342 (inner compose), #344 (client) and #347 (permanent docs). See the
[README](README.md) for the feature overview. Each backend variable's meaning is defined in
[environment-variables.md](../../environment-variables.md); this file only decides how the
standalone stack handles it.

## How values flow

`-e` / `--env-file` on `docker run`, or the client's `~/.kerghan/kerghan.env` → the Vault
container's environment → interpolation in the inner compose file → each service's
`environment:`. The inner compose file decides what each service receives. No secret is ever
baked into the image.

## Contract

| Group | Variables | Handling |
|---|---|---|
| Required secrets (no default) | `KERGHAN_SECRET_KEY`, `KERGHAN_INTEGRATIONS_KEY` | Supplied by the user, or generated by the `kerghan` client on first `up` (see [client.md](client.md#secrets)). The backend's existing boot validation fails loudly when either is missing or invalid. |
| Internal, fixed by the stack | `KERGHAN_MYSQL_HOST=mysql`, `KERGHAN_MYSQL_PORT=3306`, `KERGHAN_MYSQL_NAME`, `KERGHAN_MYSQL_USER`, `PORT`, `NODE_ENV=production`, `KERGHAN_EMAILS_ENABLED=false`, Tent's `$backendHost=http://kerghan:<PORT>` | Hard-coded in the inner compose file and the Tent standalone configuration. Not user-facing. MySQL is never published outside the inner network. |
| Overridable, with a default | `KERGHAN_MYSQL_PASSWORD` (reused for `MYSQL_PASSWORD` / `MYSQL_ROOT_PASSWORD`) | Has a default; the user may override it. Caveat: the value is fixed when the data volume is first initialized, so an override only applies to a fresh volume (or must also be changed inside MySQL). |
| Optional pass-through (allowlist) | `FRONTEND_BASE_URL`, `KERGHAN_ALLOWED_ORIGINS`, `KERGHAN_LOG_LEVEL`; the TTL, rate-limit and integrations tuning variables (`KERGHAN_*_TTL_MS`, `KERGHAN_AUTHORIZATION_REQUEST_*`, `KERGHAN_ACCOUNT_EDIT_*`, `KERGHAN_INTEGRATIONS_MAX_PER_USER`, `KERGHAN_INTEGRATIONS_CREDENTIAL_*`, `KERGHAN_INTEGRATIONS_TEST_COOLDOWN_MS`); the GitHub OAuth App set (`KERGHAN_GITHUB_OAUTH_APP_*`) and GitHub App set (`KERGHAN_GITHUB_APP_*`); rotation (`KERGHAN_PREVIOUS_SECRET_KEYS`, `KERGHAN_PREVIOUS_INTEGRATIONS_KEYS`) | Listed by name only in the `kerghan` service's `environment:` (an explicit allowlist), so each reaches the backend only when set. A variable not on the list never reaches the backend. |
| Standalone / Vault level | Host port (client `-p` / `port=` or `docker run -p <port>:80`), `VAULT_DOCKERD_TIMEOUT`, `COMPOSE_UP_ARGS` | Consumed by Vault or the client, not the backend. The offline variant bakes `COMPOSE_UP_ARGS="--pull never"`. Not secrets. |
| Excluded | `KERGHAN_EMAIL_*`, `KERGHAN_DEMO_PASSWORD` | Email is out of scope. The demo user stays as-is (see [README](README.md#known-limitations)). |

The allowlist is written out by name in the inner compose file; the wildcard notation above is
shorthand for the variables of that family listed in `environment-variables.md`. A variable
added to the backend later is not passed through until it is added to the allowlist.

The `KERGHAN_*_TTL_MS` family also includes `KERGHAN_PASSWORD_RESET_TOKEN_TTL_MS`, which the
backend reads but `environment-variables.md` does not list yet. `KERGHAN_TRUSTED_PROXY_HOPS` is
not passed through: its default (`1`) matches the single Tent hop of the stack.

## FRONTEND_BASE_URL

- The `kerghan` client passes `FRONTEND_BASE_URL=http://localhost:<port>` by default, unless
  `kerghan.env` sets it. This makes `OriginGuard` trust the origin for older browsers (see
  [stack.md](stack.md#same-origin-and-originguard)) and provides the base URL for password-reset
  links and the GitHub callback URLs.
- Plain `docker run` users set it themselves (e.g. `-e FRONTEND_BASE_URL=http://localhost:3000`).
- Because `NODE_ENV=production`, enabling the OAuth App or GitHub App types requires an `https`
  `FRONTEND_BASE_URL` (existing boot validation), which in practice means a TLS reverse proxy.

## Required tests

- A variable outside the allowlist, set on the Vault container, does not reach the backend.
- An allowlisted variable does reach it; an unset one is absent (not empty).
- Boot fails when either required secret is missing.
- The default MySQL password works on a fresh volume, and an override works on a fresh volume.
- The internal fixed values cannot be overridden from the Vault container's environment.
